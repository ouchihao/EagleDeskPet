# 大头鹰需求池与产品路线图

## 1. 产品方向

一只有小脾气、能慢慢养熟的桌面饭搭子，兼任 AI 与 GitHub 的消息小信使。

优先补齐三种反馈：饱食度和心情影响表现；互动得到有趣反应；成长解锁新的表演与道具。无需连接 AI，也应该是一只好玩的宠物。

### 设计原则

- 角色优先：保持大头鹰的头身比例、神态和贱萌风格，不为新增玩法随意换画风。
- 轻松养成：不做死亡惩罚、强制签到、断签清零或付费救活；不让维持口粮成为负担。
- 搞怪但不捣乱：玩笑发生在宠物与虚拟道具上，不移动真实文件、不抢鼠标、不关闭窗口、不默认播放声音。
- 完整演出：用户看到的是肢体和表情自然变化，保留原地脚点和完整动画阶段。
- 本地优先：养成和基础互动不需要账号、API Key、服务器或对话记忆。
- 真实传话：外部工具明确报告什么，宠物才展示什么，不把回复结束解释成任务成功。
- 渐进扩展：先做少量完成度高的内容，不在 Demo 阶段建设大型商店、插件市场或联机社区。

## 3. 优先级与需求索引

- **P3：后续方向**，先留清楚边界，数值和实现方案需要进一步设计。

需求状态使用“待设计 / 待排期 / 已交付 / 暂缓”。“待排期”表示方向已收录，不表示已开工。开始拆任务后，具体进度以关联 Issue 为准；只有验收通过且记录交付版本后才改为“已交付”。

## 4. 优先需求

<a id="req-001"></a>
### REQ-001 · 情绪与互动反应

**价值：**让人感觉在和一只宠物互动，而不只是点击按钮播放同一段动画。

范围：

- 根据已有饱食度、心情、近期互动选择反应。首批不增加必须照顾的新生命指标，也不需要大模型。
- 饥饿反应候选：抱空碗、翻碗给你看；低心情反应候选：背身闹别扭、偷偷回头。
- 摸头反应有变化：温柔摸头害羞；短时间频繁摸头时躲一下、护住发型或露出嫌弃表情。变化不等于每次重新发养成奖励。
- 碎碎念增加“当前情境”的台词分组，沿用总开关和现有每分钟节奏，不为每个状态再开一个弹话定时器。
- 新增自动情绪场景采用独立可关闭选项，默认保留站立 / 哈欠的现有待机池。手动互动与自动待机仍分开。
- 工作时不被情绪场景抢走；低饱食度提示不能绕过现有收工与喂食规则。

验收标准：

- [ ] 饥饿、低心情、连续摸头至少各有一条明确触发条件、冷却、反应和退出条件。
- [ ] 状态阈值附近不会反复进入退出；使用独立进入 / 退出阈值或等效防抖规则，数值在实现 Issue 中确认。
- [ ] 默认关闭新情绪场景时，原待机与工作行为不变；开关与设置重启后保留。
- [ ] 连续点击不会堆积大量表演、重复扣资源或绕过摸头奖励冷却；拖动不误判为点击。
- [ ] 身体、眼睛、嘴和手的过渡自然，保持原地脚点；不以整图翻转或交叉淡化代替动作。
- [ ] AI / GitHub 消息、拖动、暂停与已有气泡仍遵守优先级，不补播积压骚话。

实施前细化：首批最终姿势、触发阈值、连点判定窗口、情绪恢复方式。上述动作是创意候选，不代表素材已经存在。

<a id="req-002"></a>
### REQ-002 · 成长与荣誉解锁新内容

**价值：**升级或得奖后，桌面上真的多出一段新表演或一件可用道具。

范围：

- 将已有等级、累计互动和荣誉关联到稳定的内容 ID；保留原金银铜徽章和进度。
- 首批至少形成一种动作奖励和一种装饰奖励。候选：喝茶摸鱼动作、专属饭碗、保温杯、工牌。
- 荣誉墙显示奖励说明、解锁条件、已获得状态，并提供“查看 / 展示 / 装备”的适用入口。
- 未解锁内容可以预览介绍；解锁后的主动动作进入可选交互入口，不自动混入原待机池。
- 等级数字、荣誉门槛和奖励内容的对应关系单独配置；示例不作为已确认数值。

验收标准：

- [ ] 达成条件后内容只解锁一次，重复打开面板、重启或重复处理同一事件不重复发奖励。
- [ ] 原有存档保留等级、粮食和荣誉；满足条件的老玩家可获得应得内容，但不会重复发金币等消耗性奖励。
- [ ] 未解锁 / 已解锁 / 已装备三种状态可区分；基础动作和默认工位始终免费可用。
- [ ] 用户能在实际桌面表演或场景中看见奖励，而不仅是页面里的名称。
- [ ] 奖励资源暂缺、被移除或版本不兼容时，回退默认内容且不丢失已获得记录。

实施前细化：首批奖励清单、解锁门槛、是否允许荣誉墙直接预览完整动画；先不承诺“几级必得某物”。

<a id="req-003"></a>
### REQ-003 · 猜拳小游戏

**价值：**十几秒就能完成一次互动，用输赢后的表演体现大头鹰的性格。

范围：

- 用户主动开始，选择石头 / 剪刀 / 布；一次只进行一局。
- 完整表演包含准备、出拳和结算。赢了叉腰嘚瑟；输了愣住捂脸；平局有自己的反应。
- 连败后的“暂停营业”牌子作为后续隐藏表演候选，不纳入首批最低交付要求。
- 首版不下注、不扣粮、不消耗游戏币；可给少量有上限的心情反馈，不形成无限刷经验或金币入口。
- 在持续工作时提示先收工，沿用原交互约束；可随时退出，不强迫玩满局数。

验收标准：

- [ ] 九种出拳组合的胜 / 负 / 平结果正确；宠物出拳不读取玩家选择后故意作弊。
- [ ] 准备、出拳、结果显示与动画一致；没有提前揭示结果或结果与表情相反的情况。
- [ ] 连续点击、取消、暂停、窗口关闭和重启不会重复结算、卡死或扣资源。
- [ ] 一局通常约 10–20 秒，用户可以退出；具体节奏按动画试玩调整，不绑定动画帧回调发奖。
- [ ] 完成或退出后安全收回道具并恢复站立；通知不会强制改变猜拳结果或截断演出。

实施前细化：每种结果的完整姿势、心情奖励及冷却。工资系统未上线前不预埋实际金币奖励。

<a id="req-004"></a>
### REQ-004 · 可持续的小场景

**价值：**小鹰不只独自站着，而是在自己的小工位里吃饭、休息、闹情绪。

范围：

- 共用“进入、循环、退出”的场景规范，角色、前后遮挡道具、桌面物品和特效分层。
- 首批优先一个饥饿小场景：桌子进入、抱空碗或趴桌哭、短暂循环、擦泪收场；低心情和休息场景以后追加。
- 工作场景继续沿用桌子和电脑，可逐步添加杯子、便签等道具；不改变连续办公 / 忙碌的规则。
- 饥饿场景不是锁住宠物的惩罚：用户可关闭或结束；喂食请求在安全边界收场后执行，保留最后一次有效请求，不因等动画而重复扣粮。
- 休息场景候选是枕头、眼罩；普通干饭不强制延长成复杂场景。

验收标准：

- [ ] 每个新增场景都有可单独预览的完整进入、无缝循环和退出片段，明确何时允许衔接下一行为。
- [ ] 深浅背景下没有白边；身体不穿桌，脚不漂，电脑和手的前后关系正确。
- [ ] 连续循环首尾无跳变；场景切换后无遗留桌子、特效或悬空物件。
- [ ] 取消、拖动、缩放、暂停、恢复和跨 DPI 显示时，道具与角色保持相对位置。
- [ ] 饥饿场景期间有效的喂食请求最终只执行一次；缺粮、满腹等失败不扣粮，也不会卡在退出状态。
- [ ] 大场景资源预载和释放可验证，渲染回调中不新增同步图片解码；工作场景性能不回退。

实施前细化：首批到底采用“抱空碗”还是“趴桌哭”的视觉稿、自动场景停留上限、素材和内存预算。

<a id="req-005"></a>
### REQ-005 · AI / GitHub 任务小信使

**价值：**让人知道“哪个工具的哪件事需要我”，减少重复弹泡与通知噪声。

范围：

- 扩展现有来源名称与事件去重，增加按任务更新的状态记录；同一任务的进展更新不生成一串独立气泡。
- 候选状态包括进行中、等待用户、收到回复、明确成功、明确失败。开始 / 成功 / 失败必须有来源能力支持，不能由 Stop 事件推断。
- 多来源任务互不覆盖；同一来源的不同任务也要区分。没有任务标识或能力不足时，继续采用现有“有新回复”的降级提醒。
- 普通进度尽量安静显示，等待处理或重要变化才提醒；可关闭、静音、合并和查看未读。
- 递信、举牌、拿着坏掉的小零件等是候选信使表演；首版办公和小游戏中只更新气泡 / 小标记，保留不打断主动作的原则。
- GitHub 继续基于实际通知接口；“请求评审”不被说成“CI 失败”。增加 CI 等新事件必须另列接入范围和授权，不能假定现有通知已提供。

验收标准：

- [ ] 同任务更新、不同任务并发、不同来源并发、重复与乱序事件都能确定性处理，不把已结束任务回退成旧的运行状态。
- [ ] 只有 Stop 的客户端仍显示“有新回复”，没有伪造成功、编造错误原因或假装实时监听。
- [ ] 任务标识、版本 / 时间信息、状态转移、缓存时长和过期显示策略在实现前写入接口规范；静默或断联不会冒充成功。
- [ ] 旧 MCP 客户端和现有手动 Hook 保持兼容；连接 / 安装修改仍需要用户明确操作，不绕过客户端信任。
- [ ] 气泡紧凑、来源明确，有总量与频率限制；重连不集中播报旧事件，工作动画和拖动不受影响。
- [ ] 不读取聊天全文、剪贴板或键盘内容；默认不保存敏感通知正文。任何持久化任务记录需单独定义保留期限与清除入口。

实施前细化：各客户端支持的事件矩阵、任务 ID 约定、排序与过期语义。此需求不包含通用 AI 聊天客户端、语音常驻、屏幕读取或长期记忆。

## 5. 后续经济与商店

<a id="req-006"></a>
### REQ-006 · 工作薪水与本地虚拟货币

**来源：**用户明确提出“工作除了赚经验也能赚钱”。此处的钱指纯本地游戏币，不是真实收入。

范围：

- 工资是现有工作经验之外的新增收益，不替代免费粮食或要求先付费才能开工。
- 引入钱包余额与可理解的收入提示，币种名称、工资速率和上限待设计。
- 按养成服务的有效工作时间计算，不按动画帧数、循环次数或窗口打开次数计算。
- 工作资源预载完成、养成服务确认开始工作后才开始计薪；预载等待、加载失败或开工被拒绝时不计薪。
- 取消工作时停止计薪，即便收工动画还在播放；饱食度耗尽后不再计薪。入场、转忙、退场等视觉阶段不能额外重复发钱。
- 保留未满一个结算单位的进度，避免频繁取消、重启导致多领；余额与结算进度一起可靠保存。
- 迁移旧档时不追溯历史累计工作工资。是否有一次性起始赠币，需要明确决策与唯一发放记录。
- 不与 API Token 花费绑定，不设置真实充值、兑换、交易、提现或付费道具；不建设服务器反作弊系统。

必须在开工前确定的规则：

| 决策 | 当前约束 / 待定内容 |
| --- | --- |
| 工资速率、结算单位 | 待平衡，不在需求文档中虚构已经确认的“每分钟几元” |
| 钱包与收益上限 | 待设计；必须有限值并处理溢出，不能形成负余额 |
| 暂停 / 隐藏 / 锁屏 | 保留现有暂停待机的语义，不新增工作暂停；隐藏与锁屏是否计薪待确定。如需真正暂停工作，另列需求，不能仅依据动画是否暂停计薪 |
| 休眠 / 离线 | 是否发工资待定；若启用，补算上限不高于现有 2 小时并在饥饿耗尽处截断，不与在线结算重叠 |
| 系统时间改变 | 回拨不产生奖励，前跳受结算上限约束；文案说明本地存档不是防作弊账本 |
| 忙碌阶段 / 装备加成 | 首批不增加额外倍率；今后若增加需另列平衡需求 |

验收标准：

- [ ] 工资与经验能同时获得，既有经验和免费粮食规则未被改变。
- [ ] 同一有效工作区间多次结算、重启恢复或重复加载存档不会重复发钱；不足结算单位的进度行为一致。
- [ ] 取消、饥饿耗尽、时间回拨 / 前跳，以及选定的暂停、锁屏、离线策略有确定性测试。
- [ ] 钱包、工作结算游标和存档写入失败时不出现部分发奖、静默丢钱或负余额。
- [ ] 旧档迁移保留原等级、荣誉和工作状态，不给历史累计时长补发海量工资。
- [ ] 界面能说明本次收入和余额，提示合并而非每个结算单位弹一次话；没有真实付款或账号要求。

<a id="req-007"></a>
### REQ-007 · 商店、收藏与工位换装

**来源：**用户明确提出商店以及替换桌子、电脑，形成“工作赚钱—购买喜欢的东西—装扮工位”的反馈。

范围：

- 首批只做少量常驻装饰商品：默认套装始终免费，另提供可购买的桌子、电脑，以及可选杯子 / 小摆件。
- 商店显示预览、类型、价格、解锁条件、未拥有 / 已拥有 / 已装备状态；购买前确认。
- 购买与装备分开：买到后可以不装，换回默认或已拥有商品不再收费。
- 一次购买永久拥有首批装饰；不做限时租赁、随机抽取、耐久损耗、转卖或玩家交易。
- 桌子与电脑第一版只改变外观，不改变经验、工资、饱食消耗或忙碌阈值。
- 荣誉赠送与商店购买进入同一份已拥有内容清单；已经通过荣誉得到的物品不能再被重复扣费购买。
- 每件工位装饰需要声明场景兼容性、尺寸、锚点与遮挡层，不能把任意 PNG 强行套进工作场景。
- 工作时可以在独立预览中试搭；确认装备后提示“下次进入工位生效”，不在当前循环中突然换桌或让电脑悬空。

验收标准：

- [ ] 余额充足时，扣款与获得物品是一次不可分割的保存操作；取消、失败、余额不足不扣款。
- [ ] 双击购买、重复提交、界面重开和写入失败不会重复扣钱或只扣钱未获得物品。
- [ ] 已拥有物品可重复免费装备、卸下；当前装备与待生效装备可区分，重启后正确保留。
- [ ] 每套允许出售的桌子 / 电脑组合均通过入场、工作、转忙、忙碌、两种退场的视觉验收；不兼容组合在购买或装备前明确拦截。
- [ ] 所有组合保持身体、手、桌面、电脑和火焰的正确遮挡，缩放与拖动时无脱节、漂移或白边。
- [ ] 商品下架、缺图或版本不兼容时，回退免费默认外观，保留所有权并明确提示，不再收费“修复”。
- [ ] 从 v1.8.0 升级后默认桌子和电脑不变，玩家无需购买才能继续原来的办公功能。

实施前细化：首批商品表与价格、预览形式、可兼容组合、素材预算和余额相关提示；衣服 / 全身换装不混入这次工位商品需求。

## 6. 共用质量与验收门槛

所有需求均受以下约束；不能因为单个功能已可点击就跳过：

- **动画身份与完整性**：保持全身、头身比例和根锚点；角色的眼、嘴、手和躯干逐步变化。移动道具不等于移动整只宠物；非用户拖动的原地动作不漂移。
- **播放节奏**：普通动作约 1–2 秒为起点，按内容试玩调整；场景入退场允许更长。首尾衔接与站立 2 秒规则明确，工作循环不插站立，不重复静帧凑帧数。
- **帧率与性能**：维持最高 60 Hz 时间轴与预解码播放；分别记录逻辑采样、真实窗口表现和资源占用。GIF 预览不作为实屏 60 FPS 证明。
- **输入与优先级**：拖动、菜单、双击、喂食、收工与通知互不误触；每条队列有上限、合并和取消规则，关闭窗口后不遗留计时器。
- **数据兼容**：新增字段有默认值、版本迁移和备份策略；保留老等级、粮食、荣誉、工作进度；不兼容或损坏存档不得静默覆盖。
- **奖励一致性**：金币、物品、解锁都使用稳定 ID 和单次结算语义；不会因 UI 重绘、开窗或播放动画而重复发奖。
- **可控打扰**：新主动功能有开关；保持紧凑气泡，不抢输入焦点、不积压补播；尊重减少动画设置，不默认开麦克风或声音。
- **安全与素材**：不新增真实用户文件操作、随意执行命令或隐式网络请求。代码和素材授权分别核查，不直接搬运未授权表情包。
- **交付证据**：按风险附逻辑测试、旧档迁移、隔离 GUI 验证以及深浅底 / 多尺寸的动画录屏；截图只用测试数据，隐藏私人消息。

优先沿用现有 `DuckDeskPet.Core`、WPF 窗口、动作清单、分层场景与 MCP 桥，先扩展行为和内容数据，不承诺更换语言、动画引擎或一次性推倒重构。

<a id="idea-007"></a>
### IDEA-007 · 专属下班仪式：打工鹰撤退

- 提出日期 / 来源：2026-09-08，本轮产品创意补充。
- 用户场景：让小鹰陪自己工作一段时间，手动取消工作时，希望它也有“终于下班了”的反应。
- 期待效果：小鹰停下敲键盘、合上笔记本或让电脑熄屏，放下翅膀、伸个懒腰，再收好工位；偶尔举起“明天再卷”或“本鹰已离线”的小牌子，最后原地恢复站立。忙碌状态先收回凶狠眼神并退去火焰，不能直接切成笑脸。
- 最小范围：先做一套可从普通办公和忙碌状态自然接入的完整收工表演，以及少量本地台词；这是 REQ-004 场景退场的候选增强，不另做日历、打卡或生活日志。
- 触发边界：仅在用户手动取消且本段有效工作时长达到门槛时触发，并设置冷却；门槛和冷却待试玩确认，不延迟实际停止工作与数值结算。饱食度耗尽、程序退出和启动恢复沿用各自的原处理流程，不补播庆祝。
- 可控打扰：提供可关闭选项，关闭或资源不可用时使用原退场；配套气泡遵守碎碎念开关和通知优先级，不抢焦点。允许跳过额外表演，但仍须安全收回道具；不能为了看完整仪式强迫用户延后喂食。
- 不做什么 / 风险：不判断真人是否下班，不读取电脑使用内容，不关闭真实窗口；不增加经验、金币或连续签到奖励，不鼓励反复开工刷收益。后续工位换装时须按道具类型适配，不能给台式显示器播放“合盖”。
- 待确认问题：触发门槛、冷却、默认开关、跳过入口，以及额外表演的时长与素材预算。
- 关联需求 / Issue：REQ-004；Issue 未创建。
- 结论：备选，尚未排期或实现；不改变已有需求优先顺序。

候选验收标准（转正式需求时细化）：

- [ ] 普通办公、忙碌两条路径均完整衔接，无整图淡化、脚点漂移、穿桌或残留火焰；结束后站立 2 秒再进入原待机调度。
- [ ] 取消工作时立即停止工作计时，额外动画不续发经验或未来工资；连续点击、跳过、重启不重复触发或结算。
- [ ] 自动饥饿收工和退出程序不播放庆祝；有效喂食请求可在安全收场后执行一次，不提前或重复扣粮。
- [ ] 关闭功能、触发冷却或素材缺失时稳定回退原收工；缺失新配置的旧存档仍可正常加载。

## 8. 如何管理后续开发

采用适合当前小项目的轻量方式：

| 工具 | 在本项目中负责什么 |
| --- | --- |
| 本 Markdown 文档 | 长期需求、优先顺序、边界、验收标准和新想法入口 |
| GitHub Issues | 一件可执行工作的讨论、拆分、负责人、阻碍、进度与证据；开工后是执行状态的准确信息来源 |
| Pull Request（PR） | 提交实际改动，关联需求 / Issue，展示测试和动画效果，审查通过后合并 |
| GitHub Projects | 将来并行任务变多时再加看板；当前不要求建立或维护额外看板 |

每次计划做一小块时，从 `REQ-xxx` 拆出 Issue 并把真实链接填回索引。需求范围改变时在同一个变更中更新本文；功能完成后记录验收证据和交付版本，再关闭相应任务。文档提交或 PR 合并本身不等于功能验收通过。

入门步骤见 [CONTRIBUTING.md](../CONTRIBUTING.md)，测试入口见 [开发与测试](DEVELOPMENT.md)。这里没有批量创建远端 Issues、里程碑或 Projects，索引中的“未创建”是实际状态。

GitHub 支持使用仓库文档、Issues 和 Projects 协作，不要求需求只存成某一种格式；我们的选择是先用 Markdown 保留整体设计，再按需用 Issue 执行。[GitHub 官方规划指南](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/planning-and-tracking-work-for-your-team-or-project)
