# 大头鹰 Live2D 重构计划

日期：2026-09-22 · 迁移前代码基线：`65bc99f` / v1.11.0 · 当前开发：v1.12.0-preview.1 · 关联：REQ-009

状态（更新 2026-09-23）：继续标准 Live2D，已产出首个分层鹰模型小样及官方 Core / Framework 验证工具，见 [模型小样记录](LIVE2D-MODEL-SAMPLE.md)。独立透明宿主、角色包 schema / 模板 / 离线校验工具已实现，**正式原画与绑定、19 段语义动作、6 套服装和生产 Live2D 后端仍未完成**。不再等待用户选择模型路线，也不将小样标为迁移完成。本文保留整体技术计划，需求总入口仍为 [REQUIREMENTS.md](REQUIREMENTS.md)。生产仍使用旧 PNG 后端，真实存档未因验证而改写。

## 1. 结论与范围

目标是让**原来的大头鹰**成为可以呼吸、眨眼、注视、连续改变姿态的 Live2D 桌宠，不是换成一个现成的人形看板娘。保留搞怪表情、全身互动、原地脚点、工位道具、养成和通知。

2026-09-22 补充：本重构为当前最高优先级；REQ-010 待办便签墙和 REQ-011 Windows 原生提醒已独立并行实施，不成为本计划的前置依赖。便签墙已通过 85 项独立检查及主程序 13 项联调中的真实便签 UI 用例；原生提醒已实现逻辑与通道，专用自包含 Smoke 得到 OS Accepted / History XML，但实屏横幅、点击 / 冷启动、勿扰和睡眠场景未验收。两项进度不证明 Live2D 已可用，详情统一见 [需求主文档](REQUIREMENTS.md)。角色、服装套装、桌子 / 电脑工位适配属于整体交付，不能只换一个会眨眼的模型。未来换角色的接口层、包规范和制作工具链是首版必做，不只是留一个空接口。

难度为中高：接通一个现成模型只是小样；主要工作在大头鹰拆层与绑定、完整动作制作、场景遮挡、换装与业务交接。Live2D 通常制作参数关键形状与动作曲线，不逐帧重画，但现有 GIF / PNG 帧不能自动转换成合格模型。

采用渐进迁移：保留 C# / WPF 外壳及 Core 业务；新增可替换的表现层，旧 PNG 后端继续可用。首选验证 `WPF + WebView2CompositionControl + Cubism SDK for Web`，**验证通过才定为正式路线**。不同时重写 UI、经济规则或 MCP，不直接迁往 Unity / Electron，也不在本轮改做 3D 或 Spine。

首版边界：

- 必须完成首方大头鹰模型、现有玩法与外观兼容后，才能作为默认后端发布
- 换角色的接口、能力声明、包模板、制作说明与校验工具必须建立并验证；任意 CDN 模型导入、模型市场、自动绑定不进入首版
- 不承诺现有衣服适配任意体型；同一大头鹰骨架上的换装才是首轮目标
- 不以整图淡入淡出、翻转或拉伸代替角色的动作衔接
- 不把“支持 60 Hz 时间轴”写成“已认证任何机器稳定 60 FPS”

## 3. 前置验证与发布门槛

### 3.1 SDK 与模型许可

需要分别记录角色 / 参考图、模型原工程、编辑器、Cubism SDK 和第三方组件的使用与分发条件。代码开源或 CDN 可访问不等于模型可以随应用再分发。

官方对可增加不定数量模型的 **Expandable Application** 有单独审批与出版许可要求，且说明适用于通常可豁免的个人或小规模主体。我们未来的“任意导入模型”**可能**涉及这一分类，不能仅凭免费项目自行判断豁免；固定首方大头鹰版也需按实际发布形态核对。必要时由项目发布者向 Live2D 确认，记录答复，再决定公开导入范围。这是待确认门槛，不是已取得许可或确定收费结论。[官方说明](https://www.live2d.com/en/sdk/license/expandable/)

### 3.2 桌面显示技术小样

WebView2CompositionControl 可缓解标准 WebView2 的 WPF 层级遮挡问题，但不能由此推定现有透明桌宠窗口、命中测试和性能全部兼容。先用许可允许的测试模型验证；该模型仅测接入，不冒充大头鹰最终效果。[微软 WPF 说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/platforms/wpf)

必须覆盖：透明边缘与无黑底、WPF 菜单 / 气泡层级、左键拖动 / 双击 / 右键 / 食物拖放、不抢焦点、大小调整、100% / 150% / 200% DPI、多显示器、锁屏 / 睡眠恢复、WebGL 上下文丢失和浏览器进程失败。

输入行为对齐旧版；是否让完全透明区域穿透鼠标单列实测，不默认把整个矩形窗口都变成可点击区域。模型命中区与桌宠拖动不能相互抢事件。

### 3.3 60 Hz 与分发

- 首选一个本地 WebGL 舞台，同时画角色及工位；不每帧把 PNG 截图传回 C#，也不通过 JS 桥每帧发送全部参数
- 模型动作渲染由浏览器动画回调采样，C# 持有行为语义与动作实例；用单调时间同步与低频校正，暂停 / 恢复要显式同步
- 工资与提醒继续由宿主按真实时间结算，浏览器节流、掉帧或重建不得改变结果
- 记录父子进程总内存、CPU / GPU、冷启动、暖机和切装时间，不能只看主 EXE 或单一回调计数
- WebView2 Runtime 是新的分发依赖；P0 决定 Evergreen 或 Fixed Version，并测试缺失 Runtime、断网、公司策略限制与更新后的兼容性，不再默认承诺一个 EXE 即无条件运行
- 未具备运行条件时保留旧后端；不得未经用户同意下载 / 安装系统组件

分发方式与 Runtime 维护成本须依据微软文档选择。[WebView2 分发说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

若 P0 的透明、输入或性能门槛失败，保留旧版并形成决定记录：评估 Native SDK 离屏合成，或调整需求。不要一边默认上线失败的 Web 路线，一边堆叠第二个渲染引擎救场。

## 4. 最小目标结构与时序契约

下面是拟议职责，不在计划阶段创建空项目或过度抽象：

- **玩法层**：保留 Core，拥有养成、所有权、工作状态、奖励与提醒
- **表现协调层**：管理动作请求、资源准备、动作实例、实际结束、安全换装和故障恢复
- **旧表现后端**：封装 RasterFramePlayer + WorkStageRenderer，作为兼容实现与对照
- **Live2D 表现后端**：模型、动作、表情、视线、物理及同舞台道具绘制
- **角色包**：声明动作映射、时长 / 阶段、部件、挂点、服装、资源版本和兼容范围

首批接口只覆盖准备动作、应用状态、请求换装、查询能力、命中、实际生效装备、完成 / 失败和释放资源。`IPetPresentation` 等名称仅为候选，P1 根据实际调用点收敛；不要让业务直接引用 WPF Image、BitmapSource、JS 参数名或特定 `.motion3.json` 路径。

接口验收不只看是否声明了 interface：P1 用至少两份不同参数名、资源路径和锚点的测试包 / 适配桩驱动相同业务用例，证明无大头鹰名称、像素位置或模型参数硬编码流入 Core。首方角色、动作绑定、场景道具和服装适配分别配置；新增符合契约的包不需要修改养成 / 商店 / 记事本 / 提醒服务。第二个正式角色的完整美术制作仍属于 P6，不作为首方模型的前置投入。

### 时序与事务必须保持

1. 动作分配宿主生成的实例 ID / 序号；后端实例另有 generation。完成 / 换装响应必须匹配当前实例，重复和旧 generation 消息丢弃
2. 保留准备 → 允许执行 → 播放 → 收尾 → 实际完成的生命周期。资源未准备好时，不提前扣粮、开始工资或变更装备加成
3. Live2D 实际收尾未展示，不得仅凭 C# 计时器到点解锁下一次喂饭或揭晓猜拳；计时超过期限但无完成响应进入故障恢复，不无限卡住 UI
4. 可验证的完成事件只改变表现流程；金币、粮食、经验与成就由原业务事务处理一次。异常后重播动画不能重复奖励或扣款
5. 冷启动仍在实际装备准备或明确回退后执行一次 `BeginCatchUp`；离线最多 2 小时，不能因为模型加载而反复补算
6. 正常切后端 / 模型只在动作完整收尾、工位退出后进行；实际工作尚在继续时不静默撤掉装备倍率。故障中恢复到同一装备的旧后端，若不可行则暂停接受新交互并明确报告
7. MVP 先保持现有动作时长和 2 秒待机间隔；Live2D 文件的时长必须校验匹配，不任意倍速强凑。未来修改时长要同时更新动作与交接测试
8. JS 不拥有购买、余额、存档、MCP 或 GitHub 凭证权限，也不能直接触发系统命令

动作由身体姿态层控制，眨眼 / 呼吸 / 视线只作用于允许的参数。吃饭时抑制会冲突的视线或嘴部控制；忙碌时的特殊眼睛用明确部件 / 参数切换和过渡设计，不让两套眼睛半透明叠在一起。

## 5. 模型资产与角色包规范

### 5.1 必须交付的源文件

- 拆层原画：头部轮廓、双眼 / 瞳孔 / 眉、喙的开合、脸红、躯干、左右臂 / 手、双脚；补齐抬手后露出的区域
- 手型素材：握拳、摊手、剪刀、拿碗 / 餐具、敲键盘；不能依赖单一手图拉伸成所有手势
- 工作表情、害羞扭身、嘴部形状与吃饭遮挡需要单独设计；保持原表情包的比例和神态
- 可编辑 `.cmo3`、动作工程 `.can3`、拆层 PSD 或等价原稿；可运行的 `.moc3`、`.model3.json`、纹理、动作、表情、物理配置
- 源图许可 / 来源说明、SDK 兼容版本、制作说明、预览与测试数据

Cubism 的运行文件由模型与动画工程导出，只有 CDN 上的导出文件不能视为已经拿到了可继续补部件的模型原工程。[官方导出说明](https://docs.live2d.com/en/cubism-editor-manual/export-moc3-motion3-files/)

现有中性原画、表情包及动画可以作为绘制和节奏参考；衣服拆件可作为纹理起点，但须补图、重新绑定、验证拉伸。现有 UV atlas 不能当作 Live2D 模型导入。AI 制图可辅助绘制，不承诺自动产出已绑定、已验收的 Cubism 工程。

### 5.2 角色包必须明确的内容

| 契约项 | 必须说明 |
| --- | --- |
| 标识 | 稳定角色 ID、包版本、契约版本、渲染后端、导出 / SDK 兼容版本 |
| 能力 | 完整支持、预览支持、缺失的行为；缺动作不能伪装成完整养成角色 |
| 动作 | 语义 ID 到模型动作 / 参数的映射，时长、循环段、入场 / 收尾、手势保持段、参数控制优先级 |
| 参数 | 语义参数到模型参数的映射、最小 / 最大 / 默认值、每层控制权；不假定不同模型使用相同 ID |
| 坐标与交互 | 模型空间到舞台空间的变换、固定脚点、头 / 身命中区、气泡 / 嘴 / 双手 / 饭碗 / 键盘挂点 |
| 场景 | 前后层级、遮挡方案、桌面高度、人物与电脑间距、物理运动边界 |
| 装备 | 商品 ID 到本角色外观的映射、兼容槽位、互斥部件、实际装备确认 |
| 资源 | 允许的文件类型、完整性哈希、纹理 / 内存 / 下载规模上限、资源根目录 |
| 发布信息 | 来源、授权范围、是否允许再分发 / 修改；源工程和运行包分别管理 |

不得因为换角色重置余额、等级或收藏。缺失某件衣服时，不自动清除已购记录、退款、换成默认装仍保留高额加成，或把失败伪装成换装成功。

项目契约使用独立的 `character-package.json` 等清单包裹官方 `model3.json`，不篡改官方文件结构塞入购买或养成规则。六套大头鹰优先共用主骨架、参数约定与 19 段动作曲线，而不是重做 6×19 套独立动画；每套仍须分别验收变形与遮挡。单模型切换服装部件或多个共享动作的模型变体，在 P2 用纹理、遮罩与内存实测决定，不假设隐藏部件完全没有开销。

交付面向后续创作者的模板、字段规范、源工程组织、拆层 / 绑定 / 导出 / 预览步骤，以及能指出缺动作、缺挂点和不兼容衣服的校验工具。用户可以自行新制图像和模型后按规范接入，不必改业务代码；图像生成与可驱动模型绑定不是同一步，也不承诺任意体型共享大头鹰衣服。

首个正式版本只内置经验证的首方包；同时交付创作者模板、离线校验和开发预览接入流程，供用户制作与验证新包，但暂不开放终端用户任意包 / CDN 导入入口。后续 CDN 导入也只引入验证过的模型数据，不加载模型附带的任意网页、JS、远程插件或宿主对象；下载后固定版本并缓存，本地舞台禁止任意外部导航。桥接消息按来源、结构、大小、实例和能力白名单验证。[WebView2 安全指南](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security)

### 5.3 工位遮挡是独立交付项

优先在一个舞台里组合角色与桌电脑，不把 Live2D 整张画布简单夹在现有 WPF Images 中间。原场景的语义顺序为：火焰、身体、桌背 / 桌面、手臂或碗前景、桌前沿、电脑。

可验证方案包括：在首方模型中设置专用道具 drawable / 遮挡结构，或提供保持原绘制顺序与裁剪关系的分层渲染通道。**具体选择由 P0 小样决定**，不能假定任意模型都可以拆成几个渲染层，更不能无视 Cubism 的遮罩和绘制顺序。

若采用分层绘制，模型动画与物理每帧只更新一次，所有绘制通道使用同一参数 / 顶点快照；不能让身体与手部作为两个独立模型分别计时，否则会产生错位或两次物理推进。

先验证最小“手在桌面上、身体在桌后”的样例，再投入整套服装。保留 `work-scenes.json` 中画布、锚点、入场时间及道具图片作为迁移输入，最终用新模型空间标定，不沿用身体颜色识别与逐帧 PNG 前景提取。

## 6. 分阶段实施与验收门槛

各阶段独立小提交；下列是完整计划的阶段边界，不代表已经全数通过。P0 只通过宿主几何体 / 透明合成子集；角色包契约与工具先行完成，不等于 P1 的生产后端抽离已完成。只有门槛通过才切换生产默认行为。

当前可核验的增量：透明几何宿主探针和真实模型 SDK 探针分开维护；后者加载自行制作的鹰模型，见 [小样证据](LIVE2D-MODEL-SAMPLE.md)。角色包工具校验 schema、资源路径 / 哈希快照与声明完整性；契约有效或声明完整不等于 `RuntimeReady`，模板不作为商品。小样探针尚未接进生产角色包加载流程，生产适配器与完整玩法仍待验收，不能据此勾选 P0～P5 或下方动作清单。

| 阶段 | 交付 | 通过条件 / 不通过时的处理 |
| --- | --- | --- |
| P0 可行性 | SDK / 模型来源记录、独立透明窗口小样、渲染方案决定、性能与分发报告 | 透明、输入、WPF 叠层、桌面遮挡样例与目标机 60 Hz 测试通过；失败保留旧版并重新选路线 |

| P2 原味模型 | 可编辑大头鹰工程，站立呼吸 / 眨眼 / 有限视线、哈欠、全身害羞及收尾 | 用户确认“还是这个大头鹰”；脚点不漂、没有僵硬贴纸感或整图转场；没通过就回到模型制作 |
| P3 核心玩法 | 默认工位 6 阶段、完整吃饭、空碗 3 阶段、动作与宿主交接 | 一碗对应一次完整表演；工作持续、30 分钟忙碌、饥饿 / 取消正确收场；无穿桌 / 残留道具 |
| P4 外观和动作等价 | 全部 19 动作、6 套装扮、7 桌 / 7 电脑、商店预览与资源可用性 | 猜拳留姿、护头、喝茶不缺失；资本家眼镜及衣服随身体运动；实际装备加成与画面一致 |

P0 的显示小样与 P2 的原画整理可以部分并行，但不在技术路线、画风和工程可编辑性未确认时制作六套完整动画。模型制作是独立工作流，不用“C# 已经能加载模型”替代素材交付。

### 动作迁移清单

- [ ] 待机：原地站立、呼吸、眨眼、受限视线，不扩大现有随机动作组
- [ ] Yawn、Shy、Eat：各约 2 秒，包含进入和完整收尾；害羞有全身扭动，哈欠闭嘴和放手连续
- [ ] WorkEnter 3.5 秒：桌子进入、电脑落到桌面后开始办公；角色不能从桌面穿出
- [ ] WorkLoop / BusyLoop 各 2 秒循环；WorkToBusy 1.5 秒；WorkExit / BusyExit 各 2 秒，循环衔接无重置闪动
- [ ] HungryEnter / HungryLoop / HungryExit：1.5 / 2 / 1.5 秒；收空碗场景再喂饭
- [ ] Tea、Annoyed：各 2 秒；与已拥有动作和连续摸头规则一致
- [ ] RpsRock / RpsPaper / RpsScissors：各 2.8 秒，保持约 0.87 秒可辨认手势；RpsWin / RpsLose 各 2.4 秒
- [ ] 普通动作完成回站立，保留原有待机调度；工作 / 饥饿循环不强制回站立

Live2D 的 motion fade 是参数混合，不是自然肢体路径的自动生成器；每个收尾和循环接口仍要制作与审片。[官方动作机制](https://docs.live2d.com/en/cubism-sdk-manual/motion/)

## 7. 数据、测试与回退

### 不改变的数据与规则

- 首轮不升级 v3 养成格式；后端选择放在兼容的独立显示配置中。角色包 ID 未来加入配置时，未知字段 / 包缺失应明确回退
- 所有商品 ID、拥有记录、价格、两位小数余额、工资余数、等级、荣誉、提醒与 AI / GitHub 配置保持不变
- 预览不写拥有权、不产生属性、不开始工作；缺资源不允许先收费后显示空白
- 工作加成以实际已生效装备计算，准备或预览不生效；切换时先按旧倍率结清时间区间
- 存档测试使用副本 / 隔离目录，不直接拿真实用户进度验证迁移或失败恢复

### 新增与保留的测试

1. **Core 与事务**：保留现有确定性测试；新增动作准备失败、重复 / 乱序完成、旧实例迟到、超时和故障恢复，验证不重扣粮 / 重发工资
2. **模型契约**：参数 / 动作缺失、时长不符、损坏文件、版本不兼容、衣服缺挂点；校验报告能阻止不完整资源上架
3. **视觉**：各动作关键阶段的透明背景、脚点、手势、嘴和眼睛、眼镜、披风、空碗与桌面遮挡；保留原版参考，但不要求两种渲染像素逐点相同
4. **组合**：6 套装扮 × 7 桌 × 7 电脑共 294 工位搭配，另测 6 套装扮 × 7 桌共 42 个饥饿场景；多进度点、深浅底、1.00 / 1.28 尺寸。6×19 个动作 / 外观组合逐项登记，每套人工观看完整吃饭、摸头、工作、猜拳，不以静态截图替代连续播放
5. **性能**：记录目标机硬件 / 分辨率 / DPI；默认尺寸暖机后连续 10 分钟接近 60 次实际呈现 / 秒、P95 间隔不超过 20 ms、无重复出现的 >100 ms 卡顿作为初拟门槛；P0 先验证测量方法并标明最终采用值
6. **稳定性**：连续 2 小时工作、跨 30 分钟转忙、连续切装 / 开关预览后内存无单调增长；冷启动及后台、隐藏、睡眠后恢复另测
7. **分发与真实宿主**：普通权限、无网、Runtime 缺失 / 不兼容、模型丢失、WebGL / 子进程重建；测试拖动、双击、菜单、提醒和 AI / GitHub 模拟通知优先级

浏览器 `requestAnimationFrame` 与 WPF 回调数量只能作调度证据；物理呈现需另有测量，无法测得就明确未认证，不能套用旧版 59.67 Hz 结果证明新后端。

失败回退保留 v1.11 资源与后端，通过配置在安全边界恢复；默认不删除旧资源或减掉用户已购内容。是否以后移除旧后端，须在 Live2D 全量验收与稳定期之后单独决定。

历史测试数字见 [v1.11 验证记录](VALIDATION-v1.11.md)，仅作为旧版基线。透明几何宿主证据见 [P0 记录](LIVE2D-P0-RESULTS.md)，真实模型加载、基础绑定与调度证据见 [小样记录](LIVE2D-MODEL-SAMPLE.md)。两者都不等于完整模型质量、物理帧率或完整部署通过。

## 8. 工期判断与下一步

进入实施后，可在现有环境权限内自主选择、拉取和验证必要的开源项目与依赖，优先无需提升系统权限的方案；固定版本、记录来源 / 用途 / 许可证，并将第三方工具与项目源码隔离。无需让用户先搭建全部工具，但不能把下载成功等同于能自动生成优质 Live2D 工程；遇到付费、专门分发授权或超出现有权限的步骤，应记录实际限制，不绕过。本轮已还原独立 WebView2 宿主依赖，未安装 Cubism Editor、未引入专有 Core 或制作合格模型工程。

接入层、行为抽离属于可拆分的工程工作；模型拆层、绑定、全身动作和六套衣服是最不确定的部分。目前已有独立透明宿主探针，但仍缺真实大头鹰 Cubism 工程及其在宿主中的输入 / 蒙版工位验证，不能给“几天全部完成”的可靠承诺。

用户网页的 CDN 地址 / 看板娘组件名称仅作可选参考，不是开工前置条件。当前已自行生成分层原画、制作 PSD 并离线绑定；仍需官方 Editor 工程往返验证、造型确认与连续动作审片，发布前单列 SDK / 可扩展应用授权审查。
